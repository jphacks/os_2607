# Phase 4: Supabaseによるプロフィール同期

## Goal

Supabaseを正本とする最新プロフィールを取得・更新し、公開許可とRevealに沿って表示する。

## Scope

personIDと認証の対応、公開プロフィールの読取・本人による更新、アクセス制御、SwiftDataキャッシュ、同期失敗・公開撤回。

## Out of scope

Encounter履歴・累計のクラウド同期、複数端末の累計統合、ARKit、watchOS。

## Domain assumptions

- 最新プロフィールの正本はSupabase。SwiftDataはキャッシュを保持する。
- 本人が公開を許可した情報だけを取得・保存・表示する。
- personIDはアプリ固有の永続ID。Supabaseの認証IDとの関係は明示的に設計する。
- Revealはローカル累計を参照する想定で、公開許可の代わりにはならない。

## Implementation tasks

- personIDと認証アカウントの対応、プロフィール項目と公開許可のモデルを決める。
- 本人だけが更新でき、許可のない情報を取得できないアクセス制御を設計する。
- Supabase SDKをアダプターに閉じ込め、DomainのProfileへ変換する。
- 取得・更新・再試行、キャッシュの鮮度、競合とオフライン時の挙動を実装する。
- 公開撤回・削除をキャッシュと表示へ反映する仕組みを設計する。
- Revealによる表示制御と、サーバー側で必要なアクセス制御の範囲を決める。

## Acceptance criteria

- 本人の更新がSupabaseの正本に反映され、再取得でキャッシュも更新される。
- 他人による更新と公開許可のない情報の読取を拒否できる。
- 公開許可とRevealの両条件を満たした項目だけを表示する。
- オフラインや取得失敗時にキャッシュと最新情報を区別できる。
- 公開撤回・削除が決めた期限と条件で反映される。
- Supabase SDKへの依存がDomainに入らない。

## Manual verification

1. 検証用の本人・別Personのアカウントと公開許可済みプロフィールを用意する。
2. 本人がプロフィールを更新し、別端末で取得・キャッシュ反映を確認する。
3. 累計59 / 60、179 / 180、299 / 300秒の入力で開示項目を確認する。
4. 公開許可を撤回し、再同期後のキャッシュと表示を確認する。
5. オフラインからオンラインへの復帰と更新競合を確認する。
6. 別アカウントによる不許可の読取・更新が拒否されることを確認する。

## Open questions

- 認証方式、personIDの発行と復元、アカウント削除時の扱いは何か。
- キャッシュ期限、公開撤回の反映期限、オフライン時の表示可否をどう定めるか。
- Revealを表示制御にとどめるか、サーバー側でも開示を制限するか。その場合、累計の信頼性をどう扱うか。
- 更新競合、同期頻度、再試行の条件は何か。
- 2m・10秒、3m超・15秒、60 / 180 / 300秒という仮ルールや開示項目を変更するか。変更時の既存データとの互換性はどうするか。
